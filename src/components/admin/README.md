# Administrator Components

`AdminHeader` is rendered only after the protected layout authorizes the request. Its wrapping navigation provides dashboard/public links, conditionally adds Inquiries only when the server publication boundary is visible, and includes a non-sensitive display name plus POST-backed Server Action logout control. It does not query auth state in the browser or render user IDs/tokens.

The dashboard components render one shared date range, five analytics overview metrics, a visible nine-category link-click breakdown, five responsive Recharts visualizations, accessible data tables, and two analytics activity tables. Inquiry publication adds the sixth metric and third recent-activity table. `DashboardCharts` is a Client Component for responsive charts. `DashboardRefreshControl` is a narrow Client Component that calls `router.refresh()` and receives only the last-refreshed timestamp; it does not poll or receive credentials.

`DashboardOperationalStatus` distinguishes collection disabled, write configuration missing, authenticated reporting unavailable, configured with no stored activity, and stored activity present. It shows only booleans and the newest page/link timestamps. `InquiryOperationalStatus` applies the same safe separation to inquiry intake and adds the operator's daily-check, no-notification, retention, and external-copy reminders. Configuration presence is not described as proof of live insertion; that requires separate production QA.

Recent tables are server-rendered, limited to 15 rows, and show shortened anonymous identifiers. The inquiry overview displays the requested guest name but summarizes the contact channel instead of showing the contact value. Empty, invalid-filter, database-unavailable, loading, and unexpected-error states must remain distinct.

`DashboardExportLinks` creates two fixed analytics downloads for the already validated dashboard period and conditionally adds the inquiry download only when publication is visible. `InquiryStatusSubmitButton` and `InquiryDeleteSubmitButton` receive no guest data or database ID; each reads only its enclosing form's pending state. The delete control requires a checkbox confirmation, while the Server Action and database function repeat visibility, validation, and authorization independently.
