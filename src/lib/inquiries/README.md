# Inquiry Workflow

This directory owns the public inquiry request boundary and administrator read helpers. Public submission is disabled unless `CONTACT_INQUIRY_ENABLED` is exactly `true`. The separate server-only `CONTACT_INQUIRY_VISIBLE` publication flag keeps unfinished guest/admin surfaces hidden; enabled collection always implies visibility. Visibility never enables the endpoint. A published rollback keeps visibility true while collection is false so retained-record privacy and administrator duties remain available.

The JSON request boundary streams at most 8 KiB of actual bytes and stops reading as soon as that limit is exceeded. It requires an exact browser `Origin` matching the required trusted canonical site origin; a missing, malformed, cross-site, unconfigured, or merely similar origin is rejected. Shared strict Zod validation sanitizes bounded text, requires a name/message/consent and at least one contact method, accepts either two valid preferred dates or neither, bounds guests to 1–20, rejects past/over-two-year dates, rejects Luhn-valid payment-card patterns in messages, and rejects fields outside the reviewed schema. A hidden honeypot, two-second fill-time minimum, one-day form lifetime, per-session three-per-hour limit, and global 60-per-minute limit provide layered abuse resistance without storing raw IP addresses. Rate-limit responses include the fixed window's whole-second `Retry-After` value.

Only validated values reach the service-role-only `store_contact_inquiry` function through `src/app/api/contact/route.ts`. The function hard-codes true consent, `new` status, and database time; it returns only `created`, `duplicate`, or `conflict`, never row data. Storage absence/failure returns a real unavailable response and is never presented as a successful inquiry. Logs contain fixed reason labels only, never names, contact values, messages, identifiers, or database errors.

Migration `009` makes `submission_id` and `privacy_notice_version` required with no database defaults. The enabled browser form creates a random UUID v4 for one logical submission, keeps it distinct from the session UUID used for rate limiting, reuses it after an ambiguous or failed request, and rotates it only after an accepted response. The strict request and database constraints both require UUID v4. The rendered form includes its reviewed notice version only as a freshness assertion; the server requires an exact current match and still selects the trusted value stored in the database, so a stale tab fails closed instead of being attributed to newer wording.

The storage function inserts on the unique `submission_id` and compares every stored intake field after a conflict. A new row yields `201`; an identical retry yields `200`; the same key with different details yields `409`, preserves both the existing row and current form entries, and instructs the visitor to refresh rather than pretending the edited payload was received. The browser treats an accepted HTTP status as success only when the fixed JSON body also says `received`.

Every endpoint response is JSON with private/no-store caching and no payload echo outside bounded validation messages. Storage logging uses fixed reason labels only; names, contact values, messages, submission/session identifiers, and database details must never enter logs. The feature check runs first, so the default-disabled endpoint remains a private/no-store `404` before Origin, body, rate-limit, or storage work.

Administrator inquiry reads and status updates use the authenticated request-scoped client and remain subject to RLS. Direct browser-role table DELETE stays revoked; the explicitly confirmed deletion action invokes only the one-UUID function, which independently checks approved-admin status. The protected operational panel shows only feature/configuration/reporting booleans and the newest inquiry timestamp; it never uses or displays the backend secret. Keep public writes separate from admin operations. Do not add public database policies, payment fields, email delivery, automatic booking acceptance, bulk deletion, or production data fixtures here.
